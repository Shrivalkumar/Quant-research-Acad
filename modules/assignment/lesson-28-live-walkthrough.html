Preparing for the 45-Minute Live Walkthrough

Explain the mechanism and code, modify it safely, diagnose surprises, and communicate limitations without bluffing.

  • Trace important functions and data shapes

Intuition first

The interview tests ownership: can you predict what your code will do?

Begin with the economic idea, not the metric. State the information set, feature, target or portfolio transition, fill timing, risk controls, and expected failure regime. Then describe code architecture by data flow. Be ready to explain every parameter and why its tested range was chosen.

For a live change, restate the requested behavior, identify the layer affected, predict the output, edit minimally, and run a synthetic test before the full backtest. If results surprise you, inspect shapes, timestamps, shifted values, orders, and cash in that order. An off-by-one bug is easier to see in five labeled rows than in 400,949.

Honesty is a technical skill. Say when a result is sample-specific, when survivor bias cannot be corrected, and when a risk control trades one failure for another. A clear limitation builds more confidence than an unsupported guarantee.

Questions beginners actually ask

Clear answers before we add mathematics

What if I do not know an interview answer?

State what you know, identify the missing fact, and describe the smallest test that would answer it. Honest diagnostic reasoning is stronger than an invented confident explanation.

How should I approach a live code change?

Repeat the requested behavior, identify the affected layer, predict the outcome, edit minimally, test a tiny case, then run the full harness. Explain any difference between prediction and result.

Follow the mechanism slowly

What happens first, second, third, and fourth

01

Explain from mechanism to code

Start with why the idea might work, then show data, feature, decision, fill, position, and risk flow.

02

Defend choices with records

Use parameter inventory, baselines, failed experiments, and sensitivity rather than saying a setting simply performed best.

03

Modify one layer at a time

Identify whether the request changes a feature, signal, order, fill assumption, or metric. Predict before editing.

04

Debug aloud and honestly

Use a tiny example, describe what you expected, locate the first divergence, and state limitations or uncertainty without bluffing.

Deeper explanation

How to explain code without reading it line by line

Describe the data flow first: input shapes, feature calculation, eligibility, target or orders, and harness-owned accounting. Then open the few functions where important choices live. This gives the interviewer a map before details.

For each parameter, explain units, economic role, range tested, and observed sensitivity. “It gave the best Sharpe” is not enough because it reveals optimization but not reasoning.

A disciplined live modification loop

Suppose asked to delay Task 1 by one additional bar. Identify that the requested change belongs at the target-to-fill boundary, not inside the indicator. Predict fewer or later captured moves, implement the minimal shift, and test on labeled bars.

If the full result improves, do not immediately call the delay a new edge. Explain that slower execution may coincidentally avoid historical losses and inspect whether the improvement is stable. The interviewer is evaluating reasoning under surprise.

Worked walkthrough

An off-by-one explanation

If 63-day momentum should compare close t with close t−63, a five-row toy example can prove the indexing. Print the input, shifted denominator, and result side by side. Then explain that the score is known after close t and any market order fills at t+1 open. This separates lookback indexing from execution lag—two different shifts.

Failure prevention

Common mistakes

  • Opening with “Sharpe is high” instead of mechanism
  • Editing several functions before testing
  • Running the full dataset to debug one row
  • Pretending hidden performance is guaranteed
