Preparing the Final Submission and Research Report

Package deterministic code and compress the most decision-relevant evidence into an honest three-page report.

⏱ 85 min● Concept + calculation + practice⌁ H TO H assignment linked
Learning objectives

By the end, you can…

  • Design a valid 3×3 sensitivity table
  • Compute required diagnostics consistently
  • Write failed ideas and limitations honestly
  • Perform a clean-room ZIP verification

Intuition first

A strong report makes the research reproducible, not merely impressive

Strategy files should contain only the allowed interface, parameters, and genuine helpers. The report should lead with economic intuition and implementation, then results and robustness, then limitations. Every number must be reproducible from saved code. A three-page limit rewards prioritization: one dense diagnostic table can replace several decorative charts.

A valid sensitivity grid changes two predeclared parameters over three adjacent values each while holding everything else—including evaluation logic—fixed. Year-wise return and best-year removal must use a documented equity-return method. Turnover and cost drag need explicit definitions. Task 2 top-ten trade contribution needs a denominator and treatment of open trades.

failed_ideas.md records ideas actually run, with parameters, measured results, and a reasoned interpretation. “Did not work” is incomplete. Survivorship bias should be described directionally and specifically without inventing a correction. The final ZIP must exclude data and harness.

Questions beginners actually ask

Clear answers before we add mathematics

How can three pages contain enough information?

Use one compact architecture description, one headline-results table, one robustness table, and concise failure/limitation bullets. Remove textbook definitions that the evaluator already knows.

What belongs in failed_ideas.md?

Ideas actually tested: hypothesis, exact settings, measured output, expected behavior, observed failure, and your decision. Do not invent failures to satisfy the requirement.

Follow the mechanism slowly

What happens first, second, third, and fourth

01

Freeze reproducible code

Final parameters, helpers, and interfaces must produce the reported run without manual steps.

02

Select decision-relevant exhibits

Use compact tables for headline results, years, sensitivity, delay/cost tests, and concentration. Every exhibit should answer a research question.

03

State limitations precisely

Describe survivor bias, corporate-action policy, model assumptions, and plausible failure modes without pretending to know an exact adjustment.

04

Rehearse a clean package

Unzip elsewhere, provide the public pack beside it, run both commands, time them, and confirm only allowed submission files are included.

Deeper explanation

Turn the report into an argument with evidence

Page one should answer: what is the hypothesis and how does code express it? Page two: what happened under the public harness and how stable is it? Page three: why might it fail, what ideas were rejected, and what biases remain?

Each number needs context. “Sharpe 1.3” is weaker than “Sharpe 1.3 using daily harness equity, versus 6% cash for Task 1, with X turnover and a stated sensitivity range.” Precision of definition matters more than decimal places.

Packaging is part of reproducibility

A strategy that works only from your notebook, reads an absolute path, or depends on an unlisted library is not reproducible. The evaluator runs the submitted files against an identical harness and hidden data.

Use a clean directory to expose missing imports and accidental data dependencies. Confirm deterministic output and runtime. Keep the report synchronized with the exact code packaged—not an earlier winning version.

Worked walkthrough

Best-year removal convention

Compute daily equity returns, identify the calendar year with highest compounded return, remove those daily returns, and compound the remaining sequence in chronological order. Recompute total return and risk metrics with a clearly stated annualization period. An alternative may be defensible, but use one method consistently across both tasks and explain it.

Failure prevention

Common mistakes

  • Changing logic between sensitivity cells
  • Selecting failed ideas from memory without saved numbers
  • Including the dataset in the ZIP
  • Reporting hidden-looking certainty from public data
Retrieval practice

  1. Nothing fixed
  2. All non-grid choices and evaluation logic fixed
  3. Only CAGR fixed

Answer: B. Otherwise cell differences are not attributable to the two parameters.

  2. Actual measured results and interpretation

  4. Only screenshots
